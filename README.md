# Приоритизация лидов: Задача ранжирования

Задача — ранжирование лидов по вероятности успешного действия в течение 5 дней после назначения. Модель оценивает вероятность успеха и выдает `score`, на основе которого формируется приоритетный список для оператора.

## Результаты
Модель прошла путь от базового бейзлайна до оптимизированного градиентного бустинга с глубоким Feature Engineering.

| Этап решения | Daily AP (CV) |
| :--- | :---: |
| Baseline (LogReg) | 0.49 |
| Baseline (Дерево) | 0.54 |
| LightGBM + Feature Engineering (500+ фич) | 0.65 |
| LightGBM + Feature Selection + HPO | 0.69 |
| **Финал: LightGBM + доп. FE + HPO + Ensemble (Seeds)** | **0.72** |

Также пробовался Ranker модель, но результаты оказались намного хуже.

### Анализ (EDA)
1.  Test идет строго после Train. Использована схема **Expanding Window Validation** (с gap в 5 дней), чтобы имитировать реальную работу сервиса и избежать утечек из будущего.
2.  Доля позитивных событий — 20.7%. Учтено через веса объектов (`sample_weight`), выравненных по дням.
3.  99.9% лидов имеют историю. Конверсия лидов без истории близка к 0.
4. Наибольшую важность имеют "длинные" окна активности (14/30/90 дней) и контекст событий (`ctx_seq`, `src_slot`).

### Feature Engineering
Построено более 600 признаков, разделенных на блоки:
*   **Временные признаки:** Циклическое кодирование времени (sin/cos часа и дня недели), интервалы с начала дня.
*   **Ratio и momentum признаки:** Отношения между окнами одного счётчика. Воронка leadgen, пользовательская активность.
*   **Кросс-признаки:** Комбинации категориальных признаков
*   **Events Aggregates:** 
    *   Агрегаты считаются строго по условию `event_ts < assignment_ts`.
    *   Статистики цен (`item_price_log`), интервалов между событиями (gap), уникальность контекстов.
    *   Общее количество событий и количество за временные окна
    *   Давность последнего события
    *   Тип, источник и контекст последнего события
    *   Количество активных дней и разнообразие
    *   Средняя и стандартная цена события, разница с ценой текущего лида
    *   Статистики интервалов между событиями
    *   Для каждого event_type: count all, count по окнам, has-flag, share от общего
    *   Для каждого ctx_seq: count all, count по окнам
    *   Разнообразие типов событий в окне и энтропия распределения типов
*   **Funnel and Depth:** Категоризация событий на "поверхностные" (search) и "глубокие" (contact/favorite). Расчет конверсий между уровнями воронки внутри временных окон.
*   Скорее всего создание еще дополнительных новых признаков из events (Например, кроссы) дали бы еще результат, т.к. ctx_seq является очень сильным сигналом


### Feature Selection
Использован метод **Permutation Importance** на кросс-валидации (20 повторов). 
*   Выявлено, что **80% важности** сосредоточено всего в **31 признаках**.
*   Удаление шума (сокращение с 744 до 84 фич) позволило поднять метрику на **+0.02 AP** и значительно ускорить обучение.

### Моделирование и HPO
*   **Базовая модель:** LightGBM (выбран по соотношению скорость/качество против CatBoost и XGBoost).
*   **HPO:** Оптимизация гиперпараметров через **Optuna (TPE Sampler)** на 100 итерациях.
*   **Финальное решение:** Ансамбль из моделей с разными `random_seed` для стабилизации прогноза.

## Запуск
Для воспроизведения решения необходимо последовательно запустить ноутбуки: `eda` -> `feature_engineering` -> `modeling` или есть дополнительный ноутбук `all`, который все объединяет.
